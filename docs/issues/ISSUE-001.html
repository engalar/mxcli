ISSUE-001
$Entity/id 系统属性未被索引 → 表达式推断返回 KindUnknown
状态
Open
优先级
P1 — 影响最大
CE0117 影响估计
≥10 个漏报
主要槽位
ChangeVariableAction · ChangeActionItem
验证状态
⚠ 待 mx check 验证
症状

mx check 报告 19 个 Change variable CE0117（如 Change variable HeaderId、Change variable WFInstanceId、Change variable PayerSalesAreaDataId），但 mxcli 全部漏报。

审计数据显示：ChangeVariableAction 有 344 个槽位已解析、327 个表达式类型已推断，但 mismatch = 0。

根因分析

Mendix 实体有一个特殊系统属性 id（类型 Long），是数据库主键。这个属性不出现在域模型的属性列表中，因此未被 buildEntityAttrs 索引。

当代码写 $Header/id、$Instance/id 等路径时，推断链路：

1
AttributePathExpr: Variable="Header", Path=["id"]
2
✓ cat.EntityQNOf("Header") = "WF_Engine.WFApplicationDataRequest"
3
✗ cat.AttributeKind("WF_Engine.WFApplicationDataRequest", "id") → (KindUnknown, false) — id 不在 entityAttrs 中
4
✗ 推断返回 KindUnknown → 跳过检查 → 漏报

目标变量（如 HeaderId）声明为 Long 类型，期望接收 Long 值。但 $Header/id 的推断失败，导致无法检测类型不匹配。

  • BSON 中这些 ChangeVariableAction 的具体 Value 表达式是什么？

  • macnica CE0117 中 Change variable 错误的比例中有多少是 $Entity/id 模式？
修复方向（待批准）

方案 A（推荐）：在 buildEntityAttrs 中为每个已索引实体自动添加 id 属性，类型 = KindLong。这是 Mendix 系统保证的属性，所有实体都有。

// 在 buildEntityAttrs 处理每个 entity 后：
idx.entityAttrs[qn]["id"] = exprcheck.KindLong  // Mendix 系统主键，始终为 Long

方案 B：在 inferAttrPath 中对 path[0] == "id" 做特殊处理，直接返回 KindLong（不依赖索引）。更脆弱，不推荐。

⚠ 修复前须验证：在 macnica BSON 中找到具体案例，确认 Change variable 的实际表达式确实是 $Entity/id 模式。修复后须运行 mx check 对比确认新增检出。

症状

mx check 报告 7 个 Log message 活动的 CE0117。mxcli 对 TemplateParameter/Expression 槽的检测数为 0。

静态槽注册正确：Microflows$TemplateParameter/Expression → KindString，且审计显示 macnica 共有 94 个 TemplateParameter 表达式，其中 93 个推断为 KindString，1 个推断为 KindUnknown。

矛盾：按理说应该能检测到非 String 表达式。但 7 个 CE0117 对应的表达式推断全部失败（KindUnknown）。

根因分析

TemplateParameter 的表达式槽期望 KindString。当我们推断出 KindUnknown 时，Compatible(KindUnknown, KindString) = true（保守跳过），因此漏报。

7 个失败推断的可能原因：

  1. 变量类型未索引：表达式包含 $Variable，但该变量的 VarTypeKind 返回 Unknown（如来自 Java Action 输出、或类型为 Enumeration 等未追踪类型）
  2. 多跳属性路径：$Entity/assoc/attr 形式，inferrer 对 2+ 跳路径始终返回 Unknown
  3. 复杂函数链：中间某步推断失败导致整体为 Unknown
  4. Enumeration 引用：Module.Enum.Value 形式（QNameExpr）返回 Unknown

问题的本质是：如果一个 Log message 表达式返回 Integer 或 Object（非 String），Mendix 会报 CE0117。但当该非 String 表达式本身无法被我们推断时，我们就无法检测。

需要验证的问题
  • macnica 中这 7 个 Log message CE0117 的具体表达式是什么？
  • 这些表达式属于哪种推断失败类型（变量未知 / 多跳路径 / 其他）？
  • 如果改进变量类型索引（如 ISSUE-001 修复 id 属性），是否能解锁这 7 个推断？
修复方向（待批准）

此 issue 的修复依赖于根因诊断。可能的方向：

  • 如果是变量类型问题：改进 mfVarKinds 索引覆盖（依赖 ISSUE-001 的基础）
  • 如果是多跳路径：扩展 inferAttrPath 支持有限的 2 跳推断（通过关联端点信息）
  • 如果是 Enumeration：让 QNameExpr 返回 KindEnumeration，然后 Compatible(Enumeration, String) = false 即可检测
⚠ 必须先找到这 7 个具体表达式并分类，才能选择正确的修复方向。

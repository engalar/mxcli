背景：为什么此槽被移除

原计划将 ExpressionSplitCondition/Expression 注册为期望 KindBoolean，但在对 Mx2026AIDay 的基线测试中出现 39 个假阳性（枚举分支的表达式被误报为非 Boolean）。

原因：Mendix Decision 活动有两种模式：

  • Boolean 模式：条件表达式 = Boolean（如 $Count > 0），分支为 true/false
  • Enumeration 模式：条件表达式 = 枚举属性（如 $Status），每个分支对应一个枚举值

因无法区分这两种模式，为避免假阳性，此槽被从 staticSlots 移除。

问题：4 个 Decision CE0117 仍漏报

mx check 对 macnica 报告 4 个 Decision 相关 CE0117，包括：

[CE0117] at Decision '$MatchItem/id = $Dto/CustomerBaseId'
[CE0117] at Decision '$Dto = empty or $ExistingCustomerCode = '''

这些 Decision 使用的是错误类型的表达式。注意：$MatchItem/id = $Dto/CustomerBaseId 这种比较表达式在 Mendix 中可能因为 id 属性未索引（见 ISSUE-001）导致推断失败，而非因为 ExpressionSplitCondition 未注册。

ℹ 可能已部分被其他 issue 覆盖：如果 ISSUE-001 修复后 $MatchItem/id 能推断为 KindLong，且 $Dto/CustomerBaseId 也能推断，则这个比较表达式 Long = Long → KindBoolean（比较运算），就可以通过 WhileLoopCondition 类的检查发现。但前提是此槽要重新注册。

修复方向（待批准）

方案（推荐）：重新注册此槽为 KindBoolean，但在 Compatible() 中允许 KindEnumeration 兼容 KindBoolean（因为枚举分支是合法用法）。

// In Compatible():
if actual == exprcheck.KindEnumeration && expected == exprcheck.KindBoolean {
    return true  // 枚举分支是合法的 Mendix Decision 用法
}

同时，对 KindObject、KindList、KindString、KindInteger 等非 Boolean/Enumeration 返回 false → 检出真正的错误。

⚠ 修复前必须确认：Mx2026AIDay 中被标记为枚举分支的那 39 个表达式，推断类型是 KindEnumeration 还是 KindUnknown。如果是 KindUnknown，上述方案不够（还需让 QNameExpr 返回 KindEnumeration）。

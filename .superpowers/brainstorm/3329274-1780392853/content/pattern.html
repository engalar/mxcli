IR 核心抽象模式

替换 WidgetNode 后，widget 应以哪种模式表示？

A

接口层级（Go interface）

每种 widget 是独立 struct，共同实现 Widget 接口；消费者用类型断言或 Visitor 分发

type Widget interface {
  Name() string
  ToMDL(w io.Writer, depth int)
  Accept(v Visitor)
}
type Container struct { Children []Widget }
type DataView struct { Source DataSource; Footer []Widget }
type TextBox struct { Attr AttributeRef }

✓

  • 最符合 SOLID（OCP/LSP/ISP）
  • 新 widget 只加新 struct，不改接口
  • Visitor 集中 switch 逻辑于一处

✗

  • Visitor 模式样板代码多
  • 类型断言需处理未知类型
B

带 Props 接口的改良 WidgetNode

保留 WidgetNode 外壳，但 kind-specific 数据改为接口 Props 字段，消除 nil 字段泛滥

type WidgetNode struct {
  Kind     WidgetKind
  Name     string
  Children []WidgetNode
  Props     WidgetProps // 接口，按 Kind 类型断言
}
type DataViewProps struct { Source DataSource; Footer []WidgetNode }

✓

  • 改动最小，兼容现有 IR 使用习惯
  • 消除 nil 字段
  • 不需要 Visitor 样板

✗

  • 仍需 switch on Kind
  • OCP 仍然违反（加 widget 仍改 switch）
C

sealed 代数类型（Go 模拟）

用 unexported marker interface 封闭类型集合，保证穷举性；类似 Rust enum，每个变体是 struct

type Widget interface { isWidget() }
type Container struct { Children []Widget }
func (*Container) isWidget() {}
// exhaustive switch via go-sumtype or manual
switch w := widget.(type) {
case *Container: ...
case *DataView: ...
}

✓

  • 每个 struct 完全独立
  • switch 穷举可检查（配合 go-sumtype）
  • 最符合函数式风格

✗

  • switch 仍分散在各消费者
  • Go 原生不支持穷举验证
